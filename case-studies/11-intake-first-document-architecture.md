# Killing the Folder Tree — Intake-First Document Architecture

Two document systems in the same company had started to drift apart. This is the architecture decision that stopped it, what was already running when the decision was made, and the silent bug the design review surfaced.

**Status:** Architecture decided 18 August 2026 in a whiteboard session. Roughly half the pieces were already in production before the decision; the rest is scoped, not built. Where that line falls is stated explicitly below, because a design write-up that blurs it is marketing.

---

## The problem

A construction SME's internal platform grew two places to put a document.

- A **document management store** — every file type, object storage, metadata-driven, used for contracts, drawings, order forms, signed PDFs.
- A **knowledge vault** — text extracted from supplier documentation, searchable by the sales team, feeding an AI assistant.

Both were sensible. Together they produced the classic question: *where does this file go?* And once a human answers that question differently twice, retrieval is broken — not because the file is lost, but because you have to know where someone else decided to put it.

The instinct is to fix this with a folder taxonomy. That instinct is the bug.

## The core observation: those are two different information types

A supplier warranty PDF is two things at once.

1. **The artifact.** A specific file, with a hash, a signature, a version, a legal identity. You cannot paraphrase it. It belongs in the document store, byte for byte.
2. **The knowledge inside it.** "Aluminium profiles carry a ten-year warranty on the coating." That sentence needs to be searchable, quotable, and answerable — as text, at three levels of depth.

Storing the same thing twice is not duplication if the two copies serve genuinely different retrieval questions. *"Give me the signed document"* and *"what does our warranty actually say?"* are not the same query and should not share a code path.

## The seven decisions

| # | Decision | Why |
|---|---|---|
| 1 | **Two information types, two stores.** Artifact → document store (all file types). Knowledge → vault (text only). | They answer different questions. A binary in the vault is dead weight; a paraphrase in the document store is a liability. |
| 2 | **One shared topic code links them.** A many-to-many link table between documents and topics — not a folder path. | A document can be about three subjects. A folder path forces you to pick one and lie about the other two. |
| 3 | **The vault stores text, and only text.** If it cannot become text, it is not vault material. | Removes an entire class of "should this go here?" decisions. The rule is mechanical, so nobody has to have judgement about it. |
| 4 | **Everything enters as a draft.** Nothing is live until a human accepts it. | The extraction is good. It is not good enough to publish unread into a system the sales team quotes to customers. |
| 5 | **Output is audience-layered.** Same source, different depth per role. | A field sales rep and a technical drafter need the same fact at different resolutions. Store once, project per audience. |
| 6 | **Retrieval is hybrid.** Keyword and semantic, combined. | Semantic search fails on exact product codes. Keyword search fails on "what's the warranty like on that coated stuff." Both fail alone. |
| 7 | **Intake is one controlled door, admin-only.** | This is the load-bearing one. See below. |

Decision 7 is what makes decisions 1–6 possible. You can only delete the folder tree if intake is a single controlled entry point that guarantees every item gets classified on the way in. Free-for-all upload plus no folders is not an architecture; it is a landfill.

## What was already running when this was decided

Stated precisely, because "we designed a system" and "we run a system" are different claims:

- The document store had **already been folder-free for months** — roughly 6,800 live documents, retrieved by metadata and type rather than by location. Nobody missed the folders. That was the empirical evidence the whole design rests on.
- The vault's **draft gate was already enforced in the service layer at three separate points**, not in the UI. A draft cannot be read, searched, or fed to the assistant. Enforcing it in the UI only would have meant the API was a bypass.
- **Three-depth extraction** was already running: each source document produces a short, a medium and a full representation, generated by a mid-tier model.

## What was not built

- The shared topic code linking the two stores (decision 2).
- A draft gate on the document store — the vault had one, the document store did not.
- The audience field (decision 5).
- Semantic search spanning both stores rather than the vault alone.

Estimated at roughly a week of work. Not started at time of writing.

## The bug the design review found

Writing the architecture down surfaced a defect that had been in production for months and had never produced an error.

The extraction step truncates its input at 30,000 characters. Silently. No warning, no flag on the record, no log line. A long supplier manual is ingested, an extraction is produced, the record is marked complete — and the last two thirds of the document simply do not exist in the knowledge base. Every downstream answer is confidently derived from a partial source.

This is the same failure class as a model that returns a valid-looking answer to a question it could not actually handle: **the system reports success, so no monitoring can see it.** Nothing errors. The status field says done. The only way to catch it is to check the thing itself — count what came out, not what the status column claims.

That check now exists. It was found by writing down what the system was supposed to do and then reading the code that does it.

## Lessons

- **Folder trees are a retrieval strategy for a problem you no longer have.** They exist because humans navigate hierarchies. Once retrieval is metadata plus semantics, the hierarchy is pure maintenance cost — one person's mental model, imposed on everyone who searches later.
- **You cannot delete the folders until you control the door.** Structure has to be applied somewhere. Intake-first moves it from "wherever the uploader felt like" to one enforced point.
- **Duplication across stores is fine when the stores answer different questions.** The rule that keeps it honest: one store holds the artifact, one holds the text, and neither pretends to be the other.
- **Enforce gates in the service layer, never the UI.** A UI-only gate means every API client is an authorised bypass.
- **Write the architecture down even for a system you already run.** The 30,000-character truncation had survived every code review and every day of production use. It did not survive one honest description of what the system was meant to do.
- **`status = done` is not evidence.** Count rows. Count characters. A status column reports intent, not outcome.
